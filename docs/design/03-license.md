# 오프라인 라이선스 설계

상태: **설계 확정 · 구현 착수 보류**
Phase 배정: **상용화 준비 트랙 — Phase 2와 병렬인 독립 트랙. 실질 마감은 첫 유상 납품 직전.**
근거 명세: `docs/00-spec.md` 3.2 "오프라인 라이선스 지원", 15장 상용화 준비 트랙.

이 문서는 구현 지시서가 아니라 **설계 확정본**이다. 착수 시점이 오면 이 문서의 "구현 시 병렬 단위"부터 읽는다.

## 1. 전제와 목표

### 1.1 제품 전제

- 고객 환경은 폐쇄망이다. 라이선스 서버 호출·온라인 활성화·주기적 phone-home은 **불가능**하다.
- 검증은 전적으로 **오프라인 서명 검증 + 로컬 지문 대조**로 이뤄진다.
- 반입 매체는 USB 등 물리 매체다. 사람이 파일을 들고 들어간다.

### 1.2 목표

1. 계약된 유효기간·수량 한도를 제품이 스스로 강제한다.
2. 한 벌의 라이선스가 여러 설치본에 **우발적으로 복제되는 것**을 막는다.
3. 라이선스 설치·교체·거부·만료가 감사 로그에 남는다.

### 1.3 비목표

- **위조 방지가 아니다.** 3.5절 신뢰 모델 참조.
- 사용량 과금·미터링이 아니다. 계약 한도의 초과 여부만 본다.
- 온라인 갱신·자동 연장이 아니다.

### 1.4 확정된 정책 결정

| 항목 | 결정 |
| --- | --- |
| 평가판(trial) | **없음.** 라이선스 없이는 제품을 쓸 수 없다. |
| 개발·시연 환경 | 발급 도구에서 유효기간·수량을 자유 지정(무제한 포함)한 **개발용 라이선스**로 커버한다. 별도 코드 경로를 만들지 않는다. |
| 만료 시 동작 | 유예기간 경과 후 **로그인 차단**. 단 데드락 회피 조항(4.2) 적용. |
| 발급 도구 위치 | 이 저장소 `backend/cmd/licensegen/`. **서버 이미지에는 포함하지 않는다.** |
| 서명 개인키 | 저장소·이미지·CI 어디에도 두지 않는다. 오프라인 보관. |

## 2. 하드웨어 지문

### 2.1 MAC 단독 방식이 불가한 이유

원안의 "MAC 주소 + 유효기간" 방식은 이 제품의 배포 형태에서 성립하지 않는다.

- Docker 컨테이너 안에서 읽히는 MAC은 호스트 NIC이 아니라 **veth 페어의 MAC**이며, 컨테이너 재생성마다 바뀐다.
- 배포 이미지가 distroless라 `/etc/machine-id`가 **없다**.
- `network_mode: host`로 우회하면 호스트 MAC이 보이지만, 네트워크 격리를 포기하는 대가라 **채택하지 않는다**.

따라서 단일 성분이 아니라 **다중 성분 + 부분 일치** 방식으로 간다.

### 2.2 성분 4종

| type | 출처 | 성격 |
| --- | --- | --- |
| `install_id` | 최초 기동 시 DB에 생성하는 UUID | **필수.** 이 설치본 고유값 |
| `product_uuid` | `/sys/class/dmi/id/product_uuid` | 호스트(물리/가상 머신) 고유 |
| `machine_id` | `/etc/machine-id` | 호스트 OS 설치 고유 |
| `mac` | 물리 NIC의 MAC 집합 | 호스트 하드웨어 |

각 성분은 원값이 아니라 해시로만 저장·전송한다.

```
h = SHA256( install_id ‖ type ‖ value )
```

`install_id`를 솔트로 섞으므로 같은 호스트라도 설치본이 다르면 해시가 다르다. 라이선스 파일이 유출돼도 고객사 자산의 MAC·머신 ID 원값은 복원되지 않는다.

> **원값은 DB·파일·로그 어디에도 남기지 않는다.** 지문 블록 생성 시 메모리에서만 다루고 해시만 내보낸다.

### 2.3 MAC 필터 규칙

가상 인터페이스를 걸러내지 않으면 지문이 매 재기동마다 흔들린다.

- 이름 기준 제외: `lo`, `docker*`, `br-*`, `veth*`, `tun*`, `tap*`, `cni*`
- 비트 기준 제외: locally-administered 비트가 세트된 MAC (첫 옥텟 `& 0x02 != 0`) — 컨테이너·가상 NIC 대부분이 여기 걸린다
- 본딩(`bond0`)은 슬레이브 MAC을 승계하므로 별도 처리 없이 자연히 일치한다
- 여러 NIC이 남으면 전부 성분으로 넣고, **그중 1개만 일치해도 `mac` 성분은 통과**로 본다 (NIC 증설·교체 내성)

### 2.4 수집 경로

컨테이너 안에서는 호스트 성분을 볼 수 없다. 설치 스크립트가 대신 수집해 넘긴다.

- **Compose**: 설치 스크립트가 호스트에서 성분을 읽어 `/etc/autocert/host-identity`에 줄단위 `type=value`로 기록하고, 컨테이너에 `:ro`로 마운트한다.
- **Kubernetes**: 같은 내용을 `HOST_IDENTITY` 환경변수 또는 ConfigMap으로 주입한다.
- `network_mode: host`는 쓰지 않는다.

호스트 성분 파일이 없으면 `install_id`만으로 지문이 구성된다(2.5의 `min_host_match: 0` 케이스).

### 2.5 판정 규칙

```
install_id 일치          → 하드 요구 (불일치면 즉시 실패)
호스트 성분 일치 개수 ≥ min_host_match  → 통과
```

- `min_host_match: 1`이 기본값. product_uuid / machine_id / mac 중 **하나라도** 맞으면 된다.
- 호스트 성분을 하나도 수집할 수 없는 환경(일부 관리형 K8s 등)은 발급 시 `min_host_match: 0`으로 내린다. 이 경우 지문은 `install_id` 단독이 되고, 보호 수준이 낮아진다는 것을 발급 기록에 남긴다.

### 2.6 신뢰 모델 (중요)

- 호스트 성분은 **파일에서 읽는다.** 루트 권한을 가진 고객은 그 파일을 위조할 수 있다.
- 그러므로 이 지문의 목표는 **위조 방지가 아니다.** 목표는 (a) 우발적 복제·다중 설치 방지, (b) 감사 흔적 확보다.
- TPM·DMI 직접 접근으로 위조 내성을 높이는 방안은 **비권고**다. 컨테이너에 특권 마운트·권한 상승을 요구하게 되고, 폐쇄망 고객사 보안심사에서 반려될 위험이 실제 이득보다 크다.
- 악의적 우회에 대한 방어선은 기술이 아니라 **계약과 감사 로그**다.

## 3. 라이선스 파일 포맷

### 3.1 컨테이너

```
-----BEGIN AUTOCERT LICENSE-----
<b64u(payload_json)>.<b64u(ed25519_sig)>
-----END AUTOCERT LICENSE-----
```

- 확장자 `.lic`. 텍스트라 메일·USB·복붙 어디로도 옮길 수 있다.
- **서명 대상은 파싱된 객체가 아니라 `b64u(payload_json)` 바이트 문자열 그대로다.** canonical JSON(키 순서·공백·숫자 표기) 문제를 원천 제거한다. 검증 측은 페이로드를 파싱하기 **전에** 서명부터 검증한다.

### 3.2 payload 필드

| 필드 | 설명 |
| --- | --- |
| `v` | 포맷 버전 (정수) |
| `lic_id` | UUID. 재사용 거부 판정 키 |
| `kid` | 서명키 ID. 키 회전용 |
| `customer` | `{ name, code }` |
| `edition` | 에디션 식별자 (7.1 미해결) |
| `issued_at` / `not_before` / `not_after` | RFC3339 UTC |
| `grace_days` | 만료 후 유예 일수 (4.3) |
| `fingerprint` | `{ policy: { min_host_match }, install_id, components: [{ type, h }] }` |
| `limits` | `{ certificates, sensors, users }` — 각 항목 생략 또는 `null`이면 무제한 |
| `features` | 기능 플래그 배열 (확장점) |
| `notes` | 발급 메모(자유 문자열, 화면 미표시) |

### 3.3 서명

- **Go 표준 `crypto/ed25519`만 쓴다.** 하드 규칙 "자체 암호 구현 금지"에 따라 서명·해시·난수 어느 것도 직접 만들지 않는다.
- 공개키는 `internal/license/keys/*.pub`에 두고 `go:embed`로 바이너리에 넣는다. 폐쇄망에서 키 배포 경로가 따로 필요 없게 하기 위해서다.
- `kid`로 다중 공개키를 두고 회전한다. 구버전 kid로 서명된 기존 라이선스는 계속 검증돼야 하므로, **공개키는 폐기 시점까지 이미지에 남긴다**.
- 개인키는 저장소·이미지·CI에 절대 두지 않는다. 오프라인 보관 (7.2 미해결).

## 4. 상태 머신과 강제 지점

### 4.1 상태

```
unlicensed ──(유효 라이선스 설치)──► active ──(not_after 경과)──► grace ──(grace_days 경과)──► expired
     ▲                                  │                                                        │
     └──────────────────────────────────┴────────────(새 라이선스 설치)───────────────────────────┘
```

| 상태 | 동작 |
| --- | --- |
| `unlicensed` | 최초 설치 직후. system_administrator만 로그인 가능하고, **라이선스 등록 화면·API만** 접근 가능 |
| `active` | 정상. 전 기능 |
| `grace` | **전 기능 정상 동작 + 상시 경고 배너.** 만료됐지만 아직 유예 중 |
| `expired` | system_administrator만 로그인 가능, 라이선스 등록 화면·API만 접근 가능 |

지문 불일치는 별도 취급이다.

- 호스트 성분 불일치(하드웨어 교체·이전으로 추정) → **7일 하드웨어 유예** 후 차단. 그동안 배너로 재발급을 안내한다.
- `install_id` 불일치 → **유예 없이 즉시 차단.** 다른 설치본이거나 복제본이라는 뜻이고, 이것이 막으려는 시나리오 그 자체다.

### 4.2 만료 시 로그인 차단 — 데드락 회피 조항

만료 시 "모든 로그인 차단"을 그대로 구현하면 **새 라이선스를 올릴 화면에 들어갈 수 없는 데드락**이 생긴다. 관리자가 로그인을 못 하니 업로드 UI에 도달할 수 없고, 폐쇄망이라 원격 지원으로 뚫어줄 수도 없다. 남는 수단은 DB 직접 조작뿐인데 그것은 감사 로그를 남기지 않는 우회 경로를 정상 운영 절차로 만드는 것이라 허용할 수 없다.

따라서 `expired`(및 `unlicensed`)에서는 다음만 열어둔다.

1. **system_administrator 역할만 로그인 가능.** 그 외 역할은 로그인 자체를 거부하고 `license_expired`를 반환한다.
2. 로그인한 관리자도 접근 가능한 것은 **라이선스 등록 화면과 라이선스 API뿐**이다. 인벤토리·스캔·센서·사용자 등 그 외 모든 화면·API는 조회조차 차단한다.
3. 세션·로그아웃 등 인증 자체에 필요한 최소 엔드포인트는 예외로 연다.

이 조항의 목적은 기능을 남겨주는 것이 아니라 **복구 경로 하나만 남기는 것**이다. 열어주는 범위를 넓히면 만료 강제가 무의미해진다.

### 4.3 유예기간(grace)

- 만료 즉시 차단이 아니라, `grace_days` 동안은 **정상 동작 + 상시 경고 배너**다.
- `grace_days`는 라이선스 파일 필드이므로 발급 시점에 고객별로 정한다. 폐쇄망 반입 리드타임(승인·매체 반입 절차)이 고객사마다 크게 다르기 때문이다.
- 배너에는 남은 일수와 "라이선스 등록" 화면 링크를 노출한다.

### 4.4 수량 한도

| 대상 | 세는 기준 |
| --- | --- |
| `certificates` | 인벤토리에 등록된 인증서 수 |
| `sensors` | **active** 센서 수 |
| `users` | **active** 사용자 수 |

- `targets`·`scan_jobs`는 **한도 대상이 아니다.** 스캔이 자동 생성하는 부산물이라 고객의 계약 규모를 반영하지 않는다.
- 한도의 **110%까지는 허용**한다. 초과 구간에서는 경고 배너 + `license.limit.exceeded` 감사 이벤트를 남긴다. 110%를 넘으면 신규 생성을 거부한다.
- **진행 중인 스캔의 관측 수집은 중간에 끊지 않는다.** 스캔 도중 한도를 넘겼다고 관측을 버리면 인벤토리가 조용히 불완전해지고, 그게 만료 강제보다 훨씬 나쁜 사고다. 넘긴 사실은 배너와 감사로 알리고 데이터는 받는다.

## 5. 운영 흐름

### 5.1 최초 설치

```
설치 완료 → unlicensed
  → 관리자 로그인 → 라이선스 등록 화면
  → GET /license/fingerprint 로 지문 블록 다운로드
  → USB 반출
  → 벤더 오프라인 툴: licensegen sign --fingerprint fp.json --customer ... --not-after ... --limits ...
  → .lic 파일
  → USB 반입
  → UI 업로드 (POST /license)
  → ① armor 파싱 → ② ed25519 서명 검증(kid) → ③ 지문 대조 → ④ not_before/not_after 검사
  → 저장 + 감사 license.install
  → active
```

- 검증 실패도 **`license.reject` 감사 이벤트를 남긴다.** 실패 사유(서명 불일치/지문 불일치/기간 밖/lic_id 재사용)를 분류해 기록한다. 반복 실패는 반입 절차 문제 또는 부정 시도의 신호다.

### 5.2 갱신·교체

같은 경로를 그대로 쓴다. 별도 "갱신 모드"를 만들지 않는다.

- 감사 이벤트는 `license.replace`.
- 이전 라이선스는 삭제하지 않고 `superseded` 상태로 보존한다. 어느 기간에 어떤 계약이 적용됐는지가 감사 대상이다.
- **`lic_id` 재사용은 거부한다.** 같은 파일을 두 번 올리거나 다른 설치본의 파일을 가져오는 경우를 걸러낸다.
- `not_after`가 현재 활성 라이선스보다 **이른** 라이선스는 경고 후 허용한다. 다운그레이드·계약 축소가 실재하는 시나리오이고, 막으면 정당한 운영을 방해한다.

### 5.3 하드웨어 교체

- 호스트 성분 불일치 감지 → 7일 하드웨어 유예 시작 → 그 안에 새 지문으로 재발급받아 반입.
- **긴급 이관 코드(emergency transfer code)는 만들지 않는다.** 오프라인 검증 제품에서 그런 코드는 사실상 만능 우회 키가 되고, 유출 시 회수 수단이 없다. 7일 유예가 그 역할을 대신한다.

## 6. 구현 설계

### 6.1 클럭 조작 대응

시스템 시계를 되돌려 만료를 회피하는 것에 대한 대응이다.

- `license_clock` 테이블에 단일 행 `last_seen_at`을 두고, 5분 주기로 전진시킨다.

  ```sql
  UPDATE license_clock SET last_seen_at = GREATEST(last_seen_at, now());
  ```

  기준 시각은 **앱 프로세스의 시계가 아니라 DB의 `now()`**다. 앱 컨테이너 시계는 재기동만으로도 바뀔 수 있다.
- 만료 판정에 쓰는 시각은 `max(db_now, last_seen_at)`. 시계를 되돌려도 판정 시각은 내려가지 않는다.
- `db_now < last_seen_at - 24h`이면 `license.clock_rollback` 감사 이벤트를 남긴다. 감사 로그는 append-only 해시체인이라 이 흔적을 삭제하면 체인이 깨져 그 자체가 증거가 된다.
- 보조 앵커: `SELECT MAX(occurred_at) FROM audit_events`. `license_clock`이 통째로 조작돼도 감사 로그가 남은 최신 시각을 알려준다.
- **한계**: DB까지 장악한 고객은 `last_seen_at`을 되돌릴 수 있다. 이 대응은 우발적 시계 오차와 단순한 회피를 걸러내기 위한 것이지 결정적 방어가 아니다(2.6과 같은 입장).

### 6.2 마이그레이션 `0011_license`

> 번호는 `max(existing)+1`. 최신이 0010이므로 0011. 빈 번호를 메우지 않는다.

| 테이블 | 내용 |
| --- | --- |
| `license_install` | 단일 행. `sensor_ca` 패턴 재사용(boolean PK로 행 1개 강제). `install_id`(uuid), `installed_at` |
| `licenses` | `lic_id`(UNIQUE), `kid`, `customer`, `edition`, `not_before`, `not_after`, `grace_days`, `limits`(jsonb), `fingerprint`(jsonb), `raw`(text, 원문 armor 보존), `status`, `installed_by`, `installed_at`. **`status='active'`에 대한 부분 유니크 인덱스로 활성 1행을 강제** |
| `license_clock` | 단일 행. `last_seen_at` |

### 6.3 API

| 메서드 · 경로 | 권한 | 용도 |
| --- | --- | --- |
| `GET /api/v1/license` | 전 역할 | 현재 상태·만료일·한도 사용률. 배너 렌더용 |
| `GET /api/v1/license/fingerprint` | system_administrator | 지문 블록 다운로드 |
| `POST /api/v1/license` | system_administrator | 업로드·검증·설치. 실패도 `license.reject` 감사 |
| `GET /api/v1/license/history` | system_administrator, auditor | 설치 이력(superseded 포함) |

- `backend/api/openapi.yaml`을 **같은 커밋에서** 갱신한다. 정합 테스트가 라우트↔스펙을 양방향 대조하므로 한쪽만 바꾸면 빌드가 깨진다.
- `paths:`와 `security:`의 위치 규칙을 지킨다(GOTCHAS 참조).

### 6.4 배선 권고

- `Server`에 헬퍼를 추가한다.

  ```go
  func (s *Server) protectedWrite(pattern string, h http.HandlerFunc, roles ...domain.Role)
  ```

  = `requireRoles` + 라이선스 게이트. **모든 변경 라우트를 이것으로만 등록한다.** 라우트마다 게이트를 손으로 붙이면 새 엔드포인트에서 빠뜨리는 사고가 반드시 난다.
- 만료 시 로그인 차단(4.2)은 라우트 단이 아니라 **인증 미들웨어와 로그인 핸들러 단계**에서 처리한다. 예외는 system_administrator + 라이선스 라우트 + 인증 최소 엔드포인트.
- 감사 이벤트 삽입은 트랜잭션의 **마지막 문장**이어야 한다(기존 규칙).

### 6.5 발급 도구 `backend/cmd/licensegen/`

- 이 저장소 안에 두되 **서버 이미지 빌드 타깃에서 제외한다.** `backend/Dockerfile`은 `cmd/server`만 빌드하므로, `cmd/licensegen`을 추가 타깃으로 넣지 않는 것으로 충분하다. 이미지에 발급 도구가 들어가면 고객 환경에서 자가 발급이 가능해진다.
- 서브커맨드(안): `sign`(지문 + 계약 조건 → .lic), `verify`(발급 결과 자체 검증), `inspect`(payload 덤프).
- 개발용 라이선스는 별도 코드 경로가 아니라 **같은 도구에 넉넉한 인자를 주는 것**이다. 예: 유효기간 10년, `limits` 전부 무제한, `min_host_match: 0`. 제품 코드에 "개발 모드" 분기를 만들지 않는다 — 그 분기가 곧 우회 경로가 되기 때문이다.
- 개인키는 실행 시 오프라인 매체에서 경로로 받는다. 저장소·이미지·CI 어디에도 커밋하지 않는다.

### 6.6 로그 규칙

라이선스 원문(armor 전체)·서명 바이트·MAC/machine_id/product_uuid 원값은 **어떤 로그·에러 메시지·감사 payload에도 넣지 않는다.** 남길 수 있는 것은 `lic_id`, `kid`, 성분 해시, 판정 결과뿐이다. 기존 "인증서·개인키 로그 금지" 규칙의 연장선이다.

### 6.7 구현 시 병렬 단위

착수 시 아래 순서로 쪼갠다.

```
U1  코어      internal/license (파싱·검증·지문·상태 판정) + 0011 마이그레이션 + store
      ↓
U2  API       핸들러 4종 + openapi.yaml        ∥   U4  도구·문서  cmd/licensegen + docs/manual/LICENSE.md + docker-compose(host-identity 마운트)
      ↓
U3  프론트    settings/license 화면 + 상태 배너 + lib/api.ts 타입
```

U2와 U4는 파일이 겹치지 않아 병렬 가능하다. U3은 U2의 응답 타입에 의존한다.

## 7. 미해결 질문

1. **에디션 체계와 기본 한도 수치** — `edition` 값의 목록(예: standard / enterprise)과 각 에디션의 기본 `limits` 수치가 미정이다. 영업 정책이 정해져야 확정된다. 포맷은 이미 임의 수치를 담을 수 있으므로 구현을 막지는 않는다.
2. **서명키 보관처와 회전 주기** — 오프라인 USB 보관인지 HSM인지, `kid` 회전 주기를 어떻게 잡을지 미정. 최소 요구는 "저장소·이미지·CI에 없을 것" 하나다.

## 8. 리스크

### 8.1 만료 시 로그인 차단으로 인한 고객 장애 (채택안의 리스크)

**채택되지 않은 대안**: "만료 시 쓰기(생성·수정·삭제·발급·배포)만 차단하고 조회와 만료 경보는 살려둔다."

그 대안을 채택하지 않았으므로 다음 리스크를 감수한다.

> 라이선스가 만료되면 **고객사 인증서 만료 경보도 함께 멈춘다.** 이 제품이 막으려던 사고(인증서 만료로 인한 서비스 중단)가, 라이선스 갱신 지연이라는 계약·행정 사유 때문에 발생할 수 있다. 폐쇄망 고객은 반입 절차가 길어 갱신이 며칠씩 밀리는 것이 정상이다.

완화 수단:
- `grace_days`를 고객사 반입 리드타임보다 넉넉히 잡는다(4.3).
- 만료 D-30/D-14/D-7 배너와 알림을 `grace` 진입 전부터 띄운다.

**재검토 조건**: 실제 고객 운영에서 이 사유로 경보 공백이 발생하면, 위 대안(조회·경보 생존)을 다시 검토한다. 이 절이 그때의 근거다.
