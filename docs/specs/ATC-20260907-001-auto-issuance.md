# ATC-20260907-001 — 인증서 자동발급·갱신·배포 자동화

## 사용자 원문
> "tlsmanager.certifyiddemo.com/api/api-docs/index.html API 문서 참고해서 자동발급 기능 구현하자."
> "근데 갱신을 하려면, 당연히 서버도 재기동이 필요할거야. 서버 재기동시키는것까지 가능한가?"

확인 라운드 답변(2026-09-07): 범위 넓혀 바로 착수(P2+P3 확장 승인) / 외부 API 연동 / 발급+자동 갱신 / 재기동까지 포함 / ACME 게이트웨이 먼저 / 배포는 별도 에이전트 신설 / 승인은 정책 스위치 / 우리가 키 생성(CSR 제출) / 크리덴셜은 "1번을 솔루션 관리 페이지에서 입력할 수 있도록 구현" / 배포 대상은 nginx+Apache 먼저.

## 무엇을 만드는가
내부 ACME 게이트웨이 골격(00-spec P2 골격)을 세우고, 그 뒤에 외부 TLS Manager(tlsmanager.certifyiddemo.com) 주문 API를 상위 CA 커넥터로 붙여 인증서를 자동 발급·갱신한다. 별도 배포 에이전트(신규 프로그램)를 만들어 발급·갱신된 인증서를 대상 서버(nginx·Apache)에 배포하고 reload/재기동해 적용까지 자동화한다.

## 성공 기준
- 콘솔에서 발급 요청 → (정책상 신규 발급은 사람 승인 1회) → TLS Manager 주문 → 도메인 검증 → 폴링 → 발급된 인증서가 DB에 저장되고 기존 인벤토리에 자동 등록된다.
- 만료 임박 인증서가 갱신 허용 창(잔여 유효기간 1/3 이내·최대 30일 전) 안에서 무승인 자동 재발급되고, 배포 에이전트가 nginx/Apache에 교체·reload까지 수행한다.
- 개인키는 우리 서버가 생성해 CSR만 외부에 제출하고, 저장은 암호화(AES-256-GCM 봉인 패턴 재사용), 로그·에러·외부 어디에도 평문 노출이 없다.
- TLS Manager 접속 계정(app_id/secret)은 솔루션 관리 페이지에서 입력받아 암호화 저장된다(.env·코드 하드코딩 아님).
- 발급·갱신·배포·재기동 전 단계가 AuditEvent로 남고, 배포는 허용 목록 기반 결정론적 상태 머신으로 실행된다.

## 하지 말 것
- 상대측(TLS Manager) 키 생성 방식(CSR 미제출 주문)을 쓰지 않는다.
- 크리덴셜·개인키를 코드·문서·로그·테스트 픽스처에 넣지 않는다.
- 배포 에이전트에 임의 셸 실행 능력을 주지 않는다 — 서명된 허용 목록 작업만.
- AI 생성 명령을 실행 경로에 두지 않는다.

## 범위 외
- 센서·에이전트 원격 자동 업데이트(보류 — 다음 단계).
- IIS·WebtoB 배포 지원(WebtoB는 고객 PoC 확인 선행 조건 있음 — 사업 문서 11장).
- TLS Manager 외 다른 상위 CA 커넥터 구현(게이트웨이 구조상 확장점만 남긴다).
- P1.5 9단위(별도 승인 대기 중인 기존 트랙)와 그 범위.
- 멀티테넌시·SNI·Origin/Edge 스키마(P2 스키마 설계 직전 일괄 재론 묶음 유지).

## 가정
- 데모 서버 스펙(`/api/swagger/v1/swagger.json`)이 정본이며 운영 스펙과 같다.
- 갱신 허용 창(잔여 1/3 이내·최대 30일 전)은 외부 API 제약을 그대로 따른다.
- 승인 정책 기본값: 신규 발급은 승인 요구, 자동 갱신은 무승인 — 관리자가 설정으로 변경 가능.
- 발급 주문 추적은 폴링(외부 API에 웹훅 없음) — 기존 알림 딜리버리 큐·재스캔 스케줄러 패턴을 복제한다.
- 00-spec 7.8(배포는 별도 에이전트)·P2 골격(ACME 게이트웨이 + 상위 CA 주문)과 정합 — 명세 개정 불필요.
- CSR 미제출 시 상대측 키 전달 방식은 문서 미기재이나, 우리가 키를 생성하므로 해당 없음.
- 조사 상세: `.claude/tmp/autoissue/{api-docs,codebase,sensor-deploy}/summary.md` (로컬 전용).
