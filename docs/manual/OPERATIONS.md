# INHERIT AutoCert 운영 매뉴얼

> **문서 상태**: Phase 1(인증서 인벤토리) + Phase 3a(센서) 구현 완료 기준. 아직 구현되지 않은 기능은 **(예정)** 으로 표기한다. 기능이 완료될 때마다 이 문서를 갱신한다.

모든 셸 명령은 저장소 루트(`docker-compose.yml`이 있는 위치)에서 실행한다. 일상 운영은 웹 콘솔(2장)로 하고, 셸은 상태 확인·백업·업그레이드에만 필요하다.

## 1. 일상 운영 (셸)

### 1.1 상태 확인

```sh
docker compose ps                        # 컨테이너 상태 (db는 healthcheck 결과 표시)
curl http://localhost:8080/healthz       # API 생존 확인 — HTTP 200 기대
```

### 1.2 기동 / 중지 / 재시작

```sh
docker compose up -d          # 기동
docker compose stop           # 중지 (데이터 유지)
docker compose restart backend   # 특정 서비스만 재시작
```

## 2. 웹 콘솔 운영

`http://<서버 IP>:3000` 접속 → 로그인 (계정·역할은 INSTALL.md 6.1–6.2절). 화면은 좌측 사이드바로 이동한다 — 운영 영역 **대시보드 / 인증서 / Discovery / 센서 / 알림**, 관리 영역 **사용자 / 접근 제한**(System Administrator에게만 표시), **알림 설정**(System·Security Administrator). 로그아웃은 우상단 버튼. 세션이 만료되면 로그인 화면으로 돌아간다.

### 2.1 대시보드 — 만료 현황 점검

로그인 직후 화면. 일일 점검은 여기서 시작한다.

- **KPI 카드 8종**: 전체 인증서 / 7·30·60·90일 이내 만료(누적값 — "30일 이내"는 7일 이내를 포함) / 이미 만료 / 자체 서명 / 소유자 미지정. **카드를 클릭하면 해당 조건으로 필터된 인증서 목록으로 이동**한다.
- **만료 구간 바**: 7일 이내 / 8–30일 / 31–60일 / 61–90일 구간별 분포.
- **만료 임박 인증서 표**와 **최근 등록된 인증서 표**: 행 클릭으로 상세 화면 이동.

일일 점검 권장 순서: "이미 만료" → "7일 이내 만료" 카드 확인 → 0이 아니면 클릭해 대상 목록에서 담당자 확인·갱신 조치.

### 2.2 인증서 목록 — 검색·필터·업로드

[인증서] 화면. 전 역할 조회 가능.

- **검색**: CN / SAN / Serial / Fingerprint 통합 검색 (입력 후 자동 적용, Enter로 즉시 적용).
- **필터**: 상태 / 유형 / 만료(기간·이미 만료·자체 서명·소유자 미지정). "초기화"로 전체 해제.
- **정렬·페이지네이션**: 표 헤더 클릭 정렬, 페이지 크기 선택.
- 검색·필터·정렬 상태는 **URL 쿼리에 반영**되므로, 현재 화면 주소를 복사해 다른 운영자와 공유하면 같은 조건이 재현된다.
- **CSV 내보내기**: 우상단 버튼. 현재 검색·필터·정렬 조건에 맞는 인증서 **전체**를 CSV 파일로 내려받는다 (페이지와 무관, 1회 최대 50,000행). 전 역할 사용 가능하며 결과 0건이면 비활성화된다. 파일에는 인벤토리 메타데이터(CN·DN·일련번호·지문·SAN·유효기간·알고리즘·유형·상태 등)만 담긴다 — 인증서 원문·개인키는 저장하지 않으므로 포함될 수 없다. UTF-8(BOM)이라 Excel에서 바로 열린다. 모든 내보내기는 `certificate.export` 감사 이벤트로 기록된다(3.1절).
- **인증서 등록** 패널: 파일(.pem/.crt/.cer/.der) 선택 → 등록. 신규/중복(위치만 추가) 건수가 표시된다. 개인키 포함 파일은 전체 거부된다. 등록 버튼은 System Administrator·PKI Administrator·Operator에게만 보인다. 지원 형식 상세는 INSTALL.md 3.1절.

### 2.3 인증서 상세

목록에서 행 클릭. 기본 정보(지문·일련번호·DN·SAN·유효기간·키/서명 알고리즘·유형·상태)와 **설치 위치** 표(위치별 협상 **TLS 버전** 포함)를 보여준다. 설치 위치가 없는 인증서는 Discovery 스캔으로 위치를 찾을 수 있다.

- **인증서 체인** 카드: 자신→상위→루트 순으로 발급 관계를 보여준다. 인벤토리에 저장된 상위 인증서는 클릭하면 해당 상세로 이동하며, 단계별 만료일·D-day가 표시된다. 자체 서명 CA에는 "루트 CA" 뱃지가 붙는다.
- 상위 인증서가 인벤토리에 없으면 **미보유**로 표시되고 체인이 거기서 끝난다. 해당 CA 인증서를 업로드(2.2절)하거나 스캔으로 수집하면 체인이 이어진다. 상위 매칭은 키 식별자(AKI=SKI) 정확 일치를 우선하고, 키 식별자가 없는 인증서는 발급자 DN으로 대응한다.

### 2.4 Discovery 스캔

[Discovery] 화면. 스캔 시작은 System Administrator·PKI Administrator·Operator만 가능하다 (다른 역할은 조회만).

1. **스캔 시작 폼** 입력:
   - IP / CIDR 대역 — 한 줄에 하나씩 (예: `10.0.0.5`, `10.0.0.0/24`)
   - 포트 — 콤마 나열(`443,8443`)·범위(`8000-9000`)·프리셋(`web`/`common`) 혼용 가능. **비우면 `common` 프리셋(26개)** — 문법과 프리셋 내용, 전 포트 스윕은 2.8절
   - **실행기** — 기본값 **서버 직접**. 서버가 도달할 수 없는 세그먼트를 스캔할 때는 그곳에 배치한 **센서**를 선택한다 (선택지에는 활성 상태 센서만 나온다 — 2.5절, 설치는 SENSOR.md)
   - 타임아웃(ms)·동시 연결 수 — 비우면 기본값(5000 ms / 20). 허용 범위·상한은 INSTALL.md 3.2절
2. [스캔 시작] → 우측 **스캔 작업 표**에 Job이 추가되고 진행률이 2초 간격으로 갱신된다.
3. 완료 후 표의 **발견**(수집 인증서 수)·**신규**(인벤토리에 새로 등록된 수) 확인. 신규 숫자를 클릭하면 최근 등록순 인증서 목록으로 이동한다.

**대기 중 표시** — 아직 아무도 집어가지 않은 Job은 진행률 바 대신 **대기 중** 배지로 표시되며, 누구를 기다리는지(서버 직접 / 센서 이름)와 경과 시간("3분째")이 함께 나온다. 진행 중인 스캔과 눈으로 구분된다.

- 대기가 **90초(리스 TTL)를 넘거나** 대상 센서가 활성이 아니면 배지가 **앰버색 경고**로 바뀌고 사유가 붙는다 — "…비활성화됨 — 수령 불가" / "…등록 대기 — 수령 불가".
- 센서 위임 스캔이 시작되지 않을 때 이 표시가 1차 진단 단서다. 앰버로 바뀌면 센서 프로세스·last_seen(2.5절)과 SENSOR.md 9장을 확인한다. 서버 직접 실행이 오래 대기 중이면 backend 상태를 확인한다.
- 센서가 작업을 가져가면 **수령됨** 배지("…실행 준비 중")로 바뀌고, 실제 스캔이 시작되면 진행률 바로 넘어간다.

주의사항:

- 스캔 작업 표는 **이 브라우저에서 시작한 스캔만** 보여준다 (Job 목록 API가 없어 브라우저 로컬 저장소로 추적 — Phase 1 범위). 다른 PC·브라우저에서 시작한 Job은 보이지 않는다.
- 스캔 진행 중 backend가 재시작되면 그 Job은 재개되지 않는다. 서버 직접 실행 Job은 backend 기동 시 **실패로 자동 정리**된다(오류 `server restarted`) — 진행률이 멈춘 채 영원히 남지 않는다. 같은 대상으로 새 스캔을 실행하면 된다(결과 반영은 중복 안전). 센서 위임 Job은 리스 만료(90초)로 따로 정리된다.
- 도달 불가·비-TLS 포트·TLS 1.0/1.1 전용 서버는 조용히 건너뛴다. "발견 0"이 반복되면 5장 트러블슈팅 참조.
- **센서 실행 스캔**은 서버가 아니라 센서가 가져가서(pull) 실행한다 — 센서가 미가동이면 Job이 대기 상태에서 시작되지 않고, 실행 중 센서가 죽으면 리스 만료(90초)로 실패 처리된다. 원인 확인·조치는 SENSOR.md 9장.

### 2.5 센서 — 상태 확인·비활성화

[센서] 화면. 조회는 전 역할, 등록·비활성화는 **System Administrator 전용**. 설치·등록 절차와 트러블슈팅은 **SENSOR.md**.

- **목록**: 센서별 상태(**대기**=토큰 발급 후 미등록 / **활성** / **비활성화**)와 **마지막 접속(last_seen)** 을 보여준다. 활성 센서는 유휴 시에도 5–60초 간격으로 서버를 폴링하므로, last_seen이 수 분 이상 과거면 센서 프로세스·네트워크를 점검한다 (SENSOR.md 7장).
- **등록**: [센서 등록] → 이름 입력 → 등록 토큰(24시간 유효)·CA fingerprint·enroll 명령이 **1회만** 표시된다. 창을 닫으면 재표시 불가 — 분실 시 비활성화 후 재등록.
- **비활성화**: 해당 센서의 다음 요청부터 **즉시 차단**된다(401). 되돌릴 수 없으며 재사용하려면 새로 등록한다. 미등록(대기) 센서에 쓰면 발급된 토큰 회수가 된다. 비활성화는 `sensor.disable` 감사 이벤트로 기록된다(3.1절).

### 2.6 사용자 관리

[사용자] 화면. **System Administrator 전용** — 다른 역할에는 사이드바 메뉴가 보이지 않고, 주소로 직접 들어가도 화면이 열리지 않는다. 역할 정의는 INSTALL.md 6.2절.

- **목록**: 사용자 이름·표시이름 검색, 역할 필터, 상태 필터(활성/비활성). 비활성 계정은 행이 흐리게 표시된다. 본인 계정에는 "나" 뱃지가 붙는다.
- **사용자 추가**: 사용자 이름·표시이름·역할·초기 비밀번호를 입력해 생성한다. 비밀번호 정책은 최소 12자·계정명과 동일 금지(INSTALL.md 6.1절).
- **수정**: 표시이름과 역할을 바꾼다.
- **비활성화 / 활성화**: 비활성화하면 이후 로그인이 거부된다. 다시 활성화할 수 있다.
- **비밀번호 재설정**: 관리자가 **새 비밀번호를 직접 입력**하는 방식이다. 서버가 임시 비밀번호를 만들어 돌려주지 않으므로, 입력한 값을 본인에게 별도 경로로 전달한다.

**퇴사자·사고 대응** — 비활성화와 비밀번호 재설정은 대상 사용자의 **로그인 세션을 즉시 전부 종료시킨다.** 이미 로그인해 있던 브라우저도 다음 요청부터 거부되므로, 세션 유효기간(`SESSION_TTL`, 기본 8시간)이 남아 있어도 기다릴 필요가 없다. 퇴사·계정 탈취 의심 시 이 두 가지가 즉시 효력을 갖는 조치다.

**락아웃 방지** — 제품이 스스로 잠기는 것을 막기 위해 다음은 거부된다(HTTP 409).

- 자기 자신의 계정 비활성화 / 자기 자신의 역할 변경 — 다른 System Administrator에게 요청한다.
- 마지막으로 남은 활성 System Administrator의 비활성화·역할 강등.

그래도 **관리자 계정을 잃지 않도록 주의한다.** 관리자 계정의 비밀번호를 모두 분실하면 웹 콘솔로 복구할 방법이 없다 — 운영 시작 시 System Administrator를 최소 2개 두고, 비밀번호는 조직 표준 보관 절차에 따라 관리한다.

모든 변경은 감사 로그에 남는다 — `user.update`(표시이름·역할) / `user.disable` / `user.enable` / `user.password.reset`(3.1절). 비밀번호 값·해시는 감사 기록 어디에도 담기지 않는다.

같은 작업의 API도 제공한다 (INSTALL.md 6.2절).

### 2.7 만료 알림 운영

만료가 임박한 인증서를 4채널로 알린다 — **알림함(inbox) / 메일 / 웹훅 / Syslog**. 채널별 환경변수는 INSTALL.md 5.2.1절.

**설치 직후 상태**: 기본 정책 `기본 만료 알림` 1건이 심어져 있다 — 임계값 **90 / 60 / 30 / 7 / 1일**, 채널 **알림함 단독**, 수신자 **System Administrator 역할 전체**. 즉 아무 설정도 하지 않아도 웹 콘솔 알림함으로는 알림이 온다.

#### 알림함 (전 역할)

사이드바 [알림] 화면. 안 읽은 건수는 메뉴 배지로 표시된다. 각 알림은 대상 인증서 상세로 바로 이동할 수 있고, 읽음·모두 읽음·보관 처리를 한다. **자기 앞으로 온 알림만 보인다** — 다른 사용자의 알림은 조회되지 않는다. 읽음·보관은 개인 UI 상태이므로 감사 이벤트를 만들지 않는다.

#### 알림 정책 설정

[알림] 화면의 **정책** 탭. **System Administrator·Security Administrator만** 편집할 수 있다(감사 로그: `notification.policy.create` / `.update` / `.delete`).

- **임계값**: 만료 며칠 전에 알릴지의 목록. 기본 `90, 60, 30, 7, 1`.
  - **인증서 1건에 대해 한 번에 발화하는 임계값은 항상 1개다** — 이미 도달한 임계값 중 **가장 작은 것** 하나만 알린다. 잔여 3일짜리 인증서를 스캔이 새로 발견해도 알림은 D-90·D-60·D-30·D-7이 한꺼번에 나가는 것이 아니라 **1건(임계값 7)**이다.
  - 남은 일수가 아직 어떤 임계값에도 닿지 않았으면(예: 잔여 120일, 최대 임계값 90) 알림은 나가지 않는다.
  - 이후 D-30·D-7처럼 더 작은 임계값에 닿을 때마다 그 시점에 1건씩 나간다. 정상 케이던스는 그대로다.
- **채널**: `inbox` / `email` / `webhook` / `syslog` 중 복수 선택. **환경변수로 켜지지 않은 채널을 정책에 넣으면 발송이 `skipped`로 남는다** — 정책과 채널 설정은 별개다.
- **수신자**: 담당자(owner) / 역할 / 특정 사용자 / 고정 메일주소. 담당자를 해석할 수 없으면(담당자 미지정, 담당자에게 메일 주소 없음) 고정 메일주소로 폴백하고, 그것도 없으면 `skipped`로 사유가 남는다. 메일 수신자를 쓰려면 [사용자] 화면에서 계정에 **메일 주소**를 채워야 한다.
- **대상 필터**: 환경·부서. 비우면 전체 인증서가 대상이다.
- **테스트 발송** 버튼으로 실제 채널 도달을 확인한다(감사 로그 `notification.test`).
- 정책을 여러 개 만들어 겹쳐도 **같은 인증서·같은 임계값의 알림은 1건**이고 수신자는 합집합이 된다. 정책을 겹쳐 만들었다는 이유로 같은 메일이 두 통 가지 않는다.

#### 채널 활성 여부 확인

어떤 채널이 켜져 있고 꺼진 채널은 왜 꺼졌는지는 한 곳에서 본다.

```sh
curl -H "Authorization: Bearer <token>" \
  http://localhost:8080/api/v1/notification-channels
# [{"channel":"email","enabled":false,"reason":"SMTP_HOST is not set"},
#  {"channel":"inbox","enabled":true,"reason":""}]
```

- 응답은 `{channel, enabled, reason}` **뿐이다.** 호스트·계정·비밀번호·웹훅 URL 같은 설정값은 **의도적으로 싣지 않는다** — 값을 화면에 되비추는 순간 브라우저·프록시 로그·스크린샷으로 샌다. 실제 값은 서버의 `.env`에서 확인한다.
- 같은 `reason` 문구가 backend 기동 로그의 경고에도 남는다(`docker compose logs backend`).
- 채널 설정이 잘못되어도 **그 채널만 비활성화**되고 코어 API·나머지 채널은 정상 동작한다. 증상이 조용하므로 알림이 안 온다는 신고를 받으면 이 API부터 본다.

#### 발송 이력 조회

[알림] 화면의 **발송 이력** 탭(System Administrator·Security Administrator·Auditor). API는 `GET /api/v1/notification-deliveries`.

| 상태 | 의미 |
| --- | --- |
| `pending` | 발송 대기 (재시도 대기 포함) |
| `sending` | 발송 중 |
| `sent` | 발송 완료 |
| `failed` | 재시도 상한(5회) 초과 — `last_error`에 마지막 오류 |
| `skipped` | 발송하지 않음 — 채널 비활성·수신자 해석 실패 등. `last_error`에 사유 |

- 실패는 1분 → 2분 → 4분 → 8분 → 16분 간격으로 최대 5회 재시도한 뒤 `failed`가 된다.
- **시도 횟수는 실패 횟수가 아니다.** 첫 시도에 성공한 건도 `1`로 표시된다(성공에서도 1 올린다).
- 발송 성공·실패는 감사 로그에 남기지 않는다(감사 체인 직렬화로 사용자 요청이 지연되므로). 완전한 이력은 이 표가 보유한다.
- `NOTIFY_RETENTION_DAYS`(기본 180일)가 지난 종료 건은 자동 삭제된다. 다만 **인벤토리에 그대로 남아 있는 만료 인증서의 "만료" 알림 기록은 삭제하지 않는다** — 지우면 중복 방지 키가 풀려 같은 인증서의 만료 알림이 보존 주기마다 다시 나간다. 이력을 줄이려면 만료 인증서를 인벤토리에서 정리하거나 상태를 `replaced`·`revoked`로 바꾼다.

#### 첫 설치 시 침묵 — `NOTIFY_FIRST_RUN=seed` (반드시 알 것)

**기본값 `seed`에서는 최초 판정이 "이미 지나간 임계값"을 발송하지 않고 침묵 처리한다.**

설치 시점에 인벤토리에 이미 D-45인 인증서가 있으면 D-90·D-60은 이미 지났으므로 발송되지 않는다. 이후 D-30이 되는 순간부터 정상 발송된다. 발송하지 않은 건은 이력에 침묵 처리로 남으므로 사라지지는 않는다.

- **이유**: 이것이 없으면 설치 당일 인벤토리 전체의 D-90/60/30/7/1이 한꺼번에 터진다. 수백 통의 메일이 제품 첫인상이 된다.
- **오해 주의**: 이 동작을 모르면 "설치했는데 만료 임박 인증서 알림이 안 온다 → 알림 기능이 고장났다"고 판단하기 쉽다. **정상 동작이다.** 동작 확인은 정책 화면의 **테스트 발송**으로 한다.
- 설치 당일에 기존 인벤토리 전체를 한 번 알리고 싶으면 `NOTIFY_FIRST_RUN=send`로 두고 기동한다(폭주를 감수한다는 뜻이다).
- 같은 성질의 부수 효과: 이미 D-30을 발송한 뒤 정책에 임계값 60을 추가해도 **D-60은 소급 발송되지 않는다.** 과거를 소급하면 정책 편집이 곧 스팸 폭발이 된다. 이것은 `seed`와 무관하게 **항상** 그렇다 — 임계값 선택 규칙이 "도달한 것 중 최솟값 1개"이므로 이미 지나간 임계값은 애초에 만들어지지 않는다(위 정책 설정 절).

#### 알림이 안 왔을 때 점검 순서

위에서부터 순서대로 본다. 대부분 1~2번에서 끝난다.

1. **채널이 켜져 있나** — `GET /notification-channels`의 `enabled`·`reason` 확인(위). 꺼져 있으면 `.env`를 고치고 `docker compose up -d backend`.
2. **정책이 그 인증서를 잡나** — 정책의 임계값에 해당 일수가 있는지, 대상 필터(환경·부서)가 그 인증서를 배제하지 않는지, 정책이 `enabled`인지. 그리고 인증서가 `revoked`·`replaced` 상태면 대상에서 제외된다.
3. **수신자가 해석되나** — 메일 채널이면 대상 사용자에게 **메일 주소가 있어야** 한다. 없으면 고정 수신자로 폴백하고, 그것도 없으면 `skipped`다.
4. **발송 이력의 상태를 본다** — `skipped`면 `last_error`에 이유가 그대로 있다. `failed`면 `last_error`가 SMTP·HTTP 오류를 담고 있다. `pending`에서 안 움직이면 `NOTIFY_ENABLED`와 backend 로그를 본다.
5. 여기까지 이상이 없는데 첫 설치 직후라면 **`NOTIFY_FIRST_RUN=seed`로 침묵 처리된 것**이다(위 절).

Syslog는 `SYSLOG_NETWORK=udp`일 때 **발송 성공이 수신 보장이 아니다.** 이력이 `sent`인데 수집기에 없으면 UDP 유실을 의심하고 `tcp`로 바꾼다(INSTALL.md 5.2.1절).

### 2.8 포트 자동 탐지 스캔

[Discovery] 화면. 기본 스캔 절차는 2.4절이고, 여기서는 **포트를 어떻게 지정하는가**와 **전 포트 백그라운드 스윕**을 다룬다. 시작·제어 권한은 스캔과 동일하게 System Administrator·PKI Administrator·Operator다.

#### 포트 프리셋과 문법

포트 입력란은 자유 텍스트다. 콤마로 구분해 아래를 섞어 쓴다.

| 형태 | 예 | 의미 |
| --- | --- | --- |
| 단일 포트 | `443` | 그 포트 하나 |
| 콤마 나열 | `443,8443` | 나열한 포트들 |
| 범위 | `8000-9000` | 시작–끝 (양끝 포함) |
| 프리셋명 | `common` | 아래 표의 묶음 |

프리셋 3종:

| 프리셋 | 개수 | 내용 |
| --- | --- | --- |
| `web` | 6 | 443, 4443, 8443, 9443, 10443, 8080 — 웹·관리 콘솔만 빠르게 |
| `common` | 26 | `web` + 디렉터리(636, 3269) · 메일(465, 993, 995) · FTPS(989, 990) · 메시징(5061, 5671, 8883) · 컨테이너/오케스트레이션(2376, 2379, 6443, 10250) · 레거시 관리(5986, 7002, 8834) 등. **포트를 비우면 이 값이 쓰인다** |
| `all` | 65535 | 1–65535. **백그라운드 스윕 전용** — 단발 스캔에 넣으면 400으로 거부된다 |

- 중복은 자동 제거된다. `common,443,8000-8100`처럼 겹쳐 써도 안전하다.
- 프리셋 칩을 누르면 입력란에 이름이 삽입된다. 문법 검증은 서버가 하며, 잘못된 토큰은 그 토큰을 지목한 400 오류로 돌아온다(`invalid port token "8000-"`).

> **STARTTLS 포트에서는 인증서를 얻을 수 없다 (중요)**
>
> 스캐너는 TCP 연결 직후 곧바로 TLS 핸드셰이크를 거는 **implicit TLS 전용**이다. 평문으로 시작한 뒤 프로토콜 명령으로 TLS로 승격하는 아래 포트는 **원리상 수집이 불가능**하다.
>
> | 포트 | 프로토콜 | 승격 방식 |
> | --- | --- | --- |
> | 25, 587 | SMTP | `EHLO` → `STARTTLS` |
> | 110 / 143 | POP3 / IMAP | `STLS` / `STARTTLS` |
> | 389 | LDAP | StartTLS 확장 요청 |
> | 5432 / 3306 / 1433 | PostgreSQL / MySQL / MSSQL | 각 프로토콜의 SSL 요청 |
> | 21 / 3389 | FTP / RDP | `AUTH TLS` / X.224 협상 |
>
> 넣어봐야 전부 실패로 기록되어 노이즈만 남기 때문에 **프리셋에서 의도적으로 제외했다.** 직접 지정해도 결과는 같다. 이 포트들에 붙은 인증서는 현재 **수동 업로드(2.2절)로만** 인벤토리에 넣을 수 있다. 메일·DB 서버 인증서가 스캔에서 안 잡히는 것은 결함이 아니라 이 제약이다.

#### 전 포트 백그라운드 스윕

`all`(1–65535) 같은 넓은 포트 범위는 단발 스캔으로 돌 수 없다. 대신 **스윕**을 만든다 — 대상을 청크로 쪼개 낮은 속도로 며칠에 걸쳐 도는 배경 작업이다.

1. [Discovery] 화면에서 **전 포트 백그라운드 스윕** 토글을 켠다.
2. 대상 IP/CIDR과 포트 스펙(보통 `all`), 실행기(서버 직접 / 센서)를 지정하고 시작한다.
3. 생성 응답에 **총 엔드포인트 수·청크 수·예상 완료 시각**이 표시된다.

- 스캔 순서는 값어치 순이다 — ① `common` 26포트 → ② 1–1023 → ③ 1024–49151 → ④ 49152–65535. 며칠 뒤 취소하더라도 **얻을 것은 이미 얻은** 상태가 된다.
- **예상 소요가 `SCAN_SWEEP_MAX_DAYS`(기본 30일)를 넘으면 생성이 422로 거부**되고, 응답에 실제 예상 일수가 들어간다 — "이 스윕은 약 187일이 걸립니다. 대상 범위를 줄이거나 포트 스펙을 좁혀 주세요. (제한: 30일)". 대역을 나눠 여러 스윕으로 돌린다.
- 소요 감각: /24 하나를 전 포트 스윕하면 기본 10 pps에서 **약 19일**이다. 속도 조정과 그 위험은 INSTALL.md 5.2.2절.

#### 진행률·ETA 읽는 법

스윕 카드에 아래가 표시된다.

- **진행률** = 완료 청크 수 / 전체 청크 수. 발견 인증서 수는 자식 청크의 합계다(별도 카운터를 두지 않고 매번 집계한다 — 이중 계상이 구조적으로 불가능).
- **ETA** = 남은 엔드포인트 ÷ 레이트. 청크 간 공백(`SCAN_SWEEP_CHUNK_GAP`)이 있어 실제 완료는 표시보다 조금 늦다.
- **웨이브** = 지금 몇 번째 포트 구간을 돌고 있는지(위 ①~④).

#### 일시정지 · 재개 · 취소

세 버튼 모두 **발주자에 대한 제어**이고, 이미 나간 청크는 중간에 죽이지 않는다.

| 동작 | 결과 |
| --- | --- |
| **일시정지** | 신규 청크 발주만 멈춘다. 이미 발주된 청크는 끝까지 돌고 결과도 정상 반영된다 |
| **재개** | 멈춘 지점의 다음 청크부터 발주 재개 |
| **취소** | 발주 영구 중단(되돌릴 수 없다). 진행 중 청크는 완주하고 결과는 반영된다 |

IPS 경보가 떴을 때는 **일시정지 → `SCAN_SWEEP_RATE_PPS`를 낮춰 backend 재기동 → 새 스윕 생성**이 정석이다(이미 도는 스윕의 레이트는 생성 시점 값으로 고정되므로 재개만으로는 느려지지 않는다).

#### "센서 대기" 표시

센서 실행 스윕에서 **자식 청크를 센서가 집어가지 않은 채 `SCAN_SWEEP_STALL_AFTER`(기본 10분)를 넘기면** 스윕에 "센서 대기"가 표시된다. 스윕이 고장난 것이 아니라 **아무도 작업을 가져가지 않고 있다**는 뜻이다.

원인과 조치는 단발 스캔의 대기 배지와 같다 — [센서] 화면에서 상태·last_seen 확인(2.5절) → 센서 프로세스·방화벽 점검(SENSOR.md 9장). 센서가 다시 붙으면 대기 중이던 청크부터 자동으로 진행된다.

### 2.9 접근 제한 — 출발지 IP 허용 목록

**관리 → 접근 제한** (System Administrator 전용). 이 콘솔에 접속할 수 있는 출발지 IP를 제한한다. 환경변수 설정은 INSTALL.md 5.2.3절.

#### 규칙 없음 = 제한 없음

허용 목록이 비어 있거나 활성 규칙이 하나도 없으면 **제한이 없다**(모든 출발지 허용). 설치 직후·업그레이드 직후가 이 상태이므로 이 기능이 기존 접속을 막는 일은 없다. 반대로 **첫 규칙을 추가하는 순간부터 목록 밖의 출발지는 즉시 차단**된다(backend 재기동 불필요).

차단된 요청은 로그인 화면조차 받지 못하고 403 `ip_not_allowed`가 된다 — 접근 제한이 인증보다 앞에 있기 때문이다. `/healthz`는 제한 대상이 아니다(오케스트레이터가 컨테이너를 죽이지 않게).

#### 잠금 방지 — 화면이 자기 자신을 막지 못하게 하는 장치

1. 화면 상단에 **서버가 판정한 현재 내 접속 IP**가 표시된다. 규칙을 만들기 전에 반드시 이 값을 확인한다.
2. 추가·비활성·삭제 결과로 **요청자 자신이 차단되는 변경은 서버가 409로 거부**한다(`이 변경은 지금 접속 중인 주소를 차단합니다`). 판정은 변경과 같은 트랜잭션 안에서 하므로 두 관리자가 동시에 조작해도 함께 잠기지 않는다.
3. 마지막 활성 규칙을 끄거나 지우는 것은 "제한 해제"이므로 항상 허용된다.
4. `ADMIN_IP_ALLOW_BOOTSTRAP` 대역에서 접속하면 허용 목록과 무관하게 통과하고, 그 경로에서는 잠금 방지 판정도 건너뛴다 — 실수로 잠갔을 때의 복구 경로다.

#### "현재 내 접속 IP가 내 PC 주소가 아니다"

`ADMIN_IP_TRUSTED_PROXIES`가 비어 있으면 backend는 직접 접속한 상대(= frontend 컨테이너)의 IP만 본다. 화면에 `172.x.x.x` 같은 컨테이너 주소가 보이면 이 상태이며, **그 값으로 규칙을 만들면 모든 관리자가 통과하게 되어 제한이 무의미해진다.** 화면이 이 경우 경고를 띄운다. 조치는 INSTALL.md 5.2.3절의 신뢰 프록시 대역 설정 후 backend 재기동이다.

#### 잠겼을 때 복구

| 상황 | 조치 |
| --- | --- |
| `ADMIN_IP_ALLOW_BOOTSTRAP`을 설정해 두었다 | 그 대역의 단말에서 접속해 잘못된 규칙을 지운다 |
| 설정해 두지 않았다 | `.env`에 `ADMIN_IP_ALLOW_BOOTSTRAP`을 넣고 `docker compose up -d backend` → 그 대역에서 접속해 정리 |
| 서버 셸을 쓸 수 있다 | 마지막 수단으로 DB에서 직접 비활성화한다 (감사 기록이 남지 않으므로 최후에만) |

```sh
# 최후 수단: 모든 허용 규칙 비활성화 = 제한 해제. 즉시 반영된다(최대 30초).
docker compose exec db psql -U autocert -d autocert \
  -c "UPDATE admin_ip_rules SET is_active = false;"
```

변경 3종(추가·활성 토글·삭제)은 예외 없이 감사 이벤트를 남긴다 — `admin_ip_rule.create` / `.update` / `.delete`(3.1절로 조회). 차단된 요청 자체는 감사가 아니라 backend 경고 로그에 남는다(`request blocked by admin ip allow-list`).

### 2.10 웹 콘솔 미제공 기능

감사 로그 조회 화면은 **(예정)** 이다 — 감사 로그는 API로 조회한다(3.1절). 사이드바의 CA 관리·정책·작업·감사 로그 메뉴는 Phase 2+ 자리 표시이며 비활성 상태다.

## 3. 로그 확인

```sh
docker compose logs -f backend           # API 서버 로그 실시간
docker compose logs -f frontend
docker compose logs -f db
docker compose logs --since 1h backend   # 최근 1시간
```

- **구조화 JSON 로그 / Request ID**: backend 로그는 구조화 JSON이다. 모든 API 응답에 `X-Request-ID` 헤더가 붙고, 오류 로그·감사 이벤트에 같은 `request_id`가 기록되므로 이 값으로 요청 단위 추적이 가능하다. OpenTelemetry Trace 연동은 **(예정)**.
- 보안 원칙: 인증서 본문·개인키는 로그에 출력되지 않는다. 로그에서 발견되면 제품 결함이므로 즉시 보고할 것.

### 3.1 감사 로그

다음 이벤트는 애플리케이션 로그와 분리되어 DB의 `audit_events` 테이블에 기록된다.

- 로그인 성공·실패 (`user.login`), 로그아웃 (`user.logout`)
- 사용자 생성 (`user.created`), 속성 변경 (`user.update` — 표시이름·역할), 비활성화 (`user.disable`), 활성화 (`user.enable`), 관리자 비밀번호 재설정 (`user.password.reset`). 변경 전/후 값이 남되 비밀번호 평문·해시는 어떤 이벤트에도 담기지 않는다 (2.6절)
- 권한 거부 — 허용되지 않은 역할의 API 호출 (`authz.denied`, HTTP 403과 함께)
- 인증서 업로드 — 성공은 물론 거부(개인키 포함·파싱 실패 등)도 사유 코드와 함께 기록
- 인증서 CSV 내보내기 (`certificate.export`) — 조회성 API지만 데이터 반출 경로이므로 예외 없이 기록. 감사 이벤트에는 조회 조건(검색어·필터)과 건수만 남고 인증서 데이터 자체는 담기지 않는다. 감사 기록에 실패하면 내보내기 자체가 실패한다
- Discovery 스캔 생성
- 센서 4종 — 등록 토큰 발급(`sensor.token.issue`), 등록(`sensor.enroll` — 무효·만료 토큰으로 인한 **실패도** 기록), 클라이언트 인증서 자동 갱신(`sensor.renew`), 비활성화(`sensor.disable`). 어떤 이벤트에도 토큰 평문은 담기지 않는다

조회 화면(대시보드·목록·상세 등 GET API)은 읽기 전용이므로 감사 이벤트를 만들지 않는다 — CSV 내보내기만 예외다(위 항목).

`audit_events`는 **추가 전용(append-only)** 이다. UPDATE/DELETE/TRUNCATE는 DB 트리거가 차단하며, 각 이벤트에는 직전 이벤트와 연결된 SHA-256 해시 체인 무결성 검증값(`prev_hash`/`integrity_hash`)이 기록된다.

**조회 API** — 역할이 `security_administrator` 또는 `auditor`인 계정으로:

```sh
# 사용자·이벤트 유형·기간 필터 (RFC3339)
curl -H "Authorization: Bearer <token>" \
  "http://localhost:8080/api/v1/audit/events?event_type=user.login&from=2026-08-01T00:00:00Z"
```

**무결성 검증 API** — 체인 전체를 재계산해 변조 지점을 `id` 단위로 특정한다:

```sh
curl -H "Authorization: Bearer <token>" http://localhost:8080/api/v1/audit/verify
# valid=false면 invalid[]의 hash_mismatch(행 내용 변조)·chain_broken(중간 삭제) 확인
```

- 응답의 `head_hash`(체인 꼬리 해시)는 **주기적으로 외부 매체에 기록**할 것을 권장한다. 가장 최근 이벤트들을 통째로 지우는 꼬리 삭제는 체인만으로는 탐지되지 않으며, 외부에 기록해 둔 head_hash와의 대조로만 발견된다.
- 웹 콘솔 감사 로그 화면은 **(예정)** 이다. DB 직접 조회가 필요하면 읽기만 한다:

```sh
docker compose exec db psql -U autocert -d autocert -c \
  "SELECT created_at, event_type, actor_id, target_type, target_id, result, source_ip
     FROM audit_events ORDER BY created_at DESC LIMIT 20;"
```

## 4. 백업과 복원

### 4.1 백업 (pg_dump)

```sh
docker compose exec db pg_dump -U autocert -d autocert -F c -f /tmp/autocert.dump
docker compose cp db:/tmp/autocert.dump ./backup/autocert-$(date +%Y%m%d).dump
```

- `-F c`(custom 포맷)는 압축되며 `pg_restore`로 선택 복원이 가능하다.
- 백업 파일은 AutoCert 서버 외부(별도 매체·백업 서버)에 보관한다. 인증서 메타데이터와 감사 기록이 담기므로 백업 파일 접근도 통제 대상이다.
- 권장 주기: 일 1회 + 업그레이드 직전 필수.

### 4.2 복원

```sh
docker compose cp ./backup/autocert-YYYYMMDD.dump db:/tmp/restore.dump
docker compose exec db pg_restore -U autocert -d autocert --clean --if-exists /tmp/restore.dump
```

복원은 기존 데이터를 덮어쓴다. 복원 전 backend를 중지(`docker compose stop backend`)하고, 복원 후 재기동한다.

## 5. 업그레이드 절차

1. **백업 먼저** — 4.1절 절차로 DB를 백업한다.
2. 새 버전 소스/이미지를 반입한다.
3. 재빌드·재기동:
   ```sh
   docker compose up --build -d
   ```
4. backend가 기동하면서 **새 SQL 마이그레이션을 자동 적용**한다. 별도 마이그레이션 명령이 없다.
5. 확인: `curl http://localhost:8080/healthz` 200 + 웹 콘솔 로그인·대시보드 표시 + `docker compose logs backend`에서 마이그레이션 오류 없음.

**롤백 주의**: 이전 버전 이미지로 되돌려도 이미 적용된 스키마 변경은 되돌아가지 않는다. 스키마가 바뀐 업그레이드를 되돌려야 하면 **1번에서 받은 백업으로 복원**하는 것이 표준 절차다. 마이그레이션을 수동으로 역적용하지 않는다.

| 스캔 작업 표가 비어 있음 / 이전 스캔이 안 보임 | 스캔 표는 그 브라우저에서 시작한 Job만 추적한다 (2.4절) | 결과 자체는 인벤토리에 반영되어 있다 — 인증서 목록을 최근 등록순으로 확인 |

## 8. 운영 기능 로드맵 표기

아래 기능은 스펙에 정의되어 있으나 아직 미구현이다. 완료 시 본 매뉴얼에 운영 절차가 추가된다.

- **(예정)** 감사 로그 웹 콘솔 조회·무결성 검증 화면 — 기록·API는 구현되어 동작 중이다 (3.1절)
- **(예정)** Discovery 스캔 Job 전체 목록 API — 현재는 시작한 브라우저에서만 Job 추적 (2.4절)
- **(예정)** STARTTLS 승격 포트(25·587·110·143·389·5432·3306·1433·21·3389)의 인증서 자동 수집 — 현재는 수동 업로드로만 등록 (2.8절)
- **(예정, Phase 2 이후)** CA 연동·발급·갱신·배포 자동화·에이전트(호스트 설치형)

구현 완료되어 이 표에서 빠진 항목: 인증서 수동 업로드(2.2절), 로그인·RBAC(INSTALL.md 6.1–6.2절), Discovery 네트워크 TLS 스캔(2.4절), 만료 대시보드·인증서 목록·상세 화면(2.1–2.3절), 센서(원격 수집기)를 통한 격리 세그먼트 스캔(2.5절, SENSOR.md), 웹 콘솔 사용자 관리 화면(2.6절), 만료 임박 알림 4채널(2.7절), 포트 프리셋·전 포트 백그라운드 스윕(2.8절), 관리 콘솔 접근 IP 제한(2.9절).
