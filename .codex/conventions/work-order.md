> Codex 적용: 먼저 `.codex/conventions/codex-runtime.md`를 따른다. 이식 원문의 자동 push·외부 쓰기·다음 단계는 승인된 범위에만 적용한다. 도구/하네스 관측은 Claude의 배경이며 Codex 보장으로 읽지 않는다.

# Work Order — 하나의 ID로 요구사항부터 학습까지 꿰는 규약

Work Order는 **새 계층이 아니다.** 이미 있는 범위 헌장(`docs/specs/*.md`)에 ID를 얹어 승격한 것이고,
그 ID가 스펙 → 위임 단위 → 판정 → 커밋을 관통하는 **Trace ID** 역할을 한다.
사람은 Work Order를 작성하지 않는다 — 오케스트레이터가 스펙을 확정하는 시점에 대화에서 발급한다.

**이 문서가 ID 체계의 단일 원본이다.** 다른 규약 파일은 이 경로를 1줄로 참조하고 규칙을 다시 적지 않는다.

## 1. ID 형식

```
<PREFIX>-<YYYYMMDD>-<NNN>      예: TPL-20260827-001
```

- `NNN` — 그 **날짜의** 일련번호 3자리. `001`부터 시작한다.
- 다음 번호는 카운터 파일이 아니라 **증거에서 구한다**: `docs/specs/` 파일명과
  `git log --all --grep=<PREFIX>-<YYYYMMDD>` 에 이미 나타난 최대값 + 1.
- **`PREFIX` 는 저장소마다 다르므로 `.codex/identity` 의 `work-order-prefix:` 키에서 읽는다.**
  저장소 코드·스크립트·프롬프트 어디에도 하드코딩하지 않는다.
  키가 없거나 값이 비면 **ID 를 발급하지 않고 사용자에게 1회 묻는다** — 추정으로 만들지 않는다.

## 2. 언제 발급하나 — M급 이상만

| 티어 | 예 | ID | 스펙 |
| --- | --- | --- | --- |
| S급 | 오타·문구 1줄 수정 (경량 위임 대상) | 발급하지 않는다 | 만들지 않는다 |
| M급 이상 | 스펙이 필요한 규모 — 파일 여럿 / 위임 여럿 / 검증 대상 | 발급한다 | `docs/specs/<ID>-<slug>.md` |
| 조사 단위 (산출물이 파일로 남는 것) | 결과가 `docs/research/` 같은 파일로 남는 조사 — 위임이 하나뿐이어도 | M급 기준 그대로 발급한다 | `docs/specs/<ID>-<slug>.md` — 위임장은 §6대로 그 안에 남긴다 |

S급을 제외하는 이유는 한 줄이다: **오타 수정에 ID 를 발급하는 것이 "프로세스가 제품보다 복잡해지는" 실패다.**
S급은 기존 경량 위임 경로를 그대로 쓴다.

조사를 M급에 붙이는 이유도 한 줄이다: **보고서의 전제가 위임장에서 온 것인지 조사관이 정한 것인지를 나중에 되찾는 유일한 경로가 §6의 위임장 보관이다** — 파일로 남는 보고서는 그 전제와 함께 전파되므로, 발원을 되찾을 수 없으면 정정이 재독으로 끝난다. 반환만 받고 파일이 남지 않는 짧은 1회 확인은 S급으로 남는다.

## 3. ID 가 이름 붙이는 것들

- **스펙 파일**: `docs/specs/<ID>-<slug>.md`. `slug` 는 사람이 읽기 위한 것이고 **유일성은 ID 가 보장한다.**
- **하위 작업 단위**: `<ID>-A`, `<ID>-B` … 알파벳 순.
- 이 문자열이 **그대로** 판정·상태 파일의 `<unit>` 이름이 된다. 별도 매핑표를 만들지 않는다.

  | 산출물 | 경로 |
  | --- | --- |
  | 판정 | `.codex/review/<ID>-B.verdict.md` |
  | 진행 단계 | `.codex/perf/units/<ID>-B.status` |

  (두 파일의 스키마는 각각 `.codex/conventions/verdict-protocol.md`·`status-protocol.md` 가 단일 원본이다.)

- **커밋 메시지에 ID 를 넣는다.** 이것은 권장이 아니라 **§4 의 전제 조건**이다 — 안 넣으면
  `git log --grep=<ID>` 유도가 성립하지 않고, ID 체계 전체가 이름 규칙으로만 남는다.

**왜 발급 규칙이 필요한가 (실측)**: 이름 충돌이 이미 일어났다. `.codex/perf/units/` 에
`final-polish.status` 옆에 손으로 `-2` 를 붙인 `final-polish-2.status` 가 남아 있고,
`shadcn-token-naming.status` / `shadcn-token-naming-fix.status` 도 같은 흔적이다.
지금의 `<unit>` 은 위임이 즉석에서 준 주제 kebab 일 뿐 **발급 규칙이 없다.**

## 4. 상태는 저장하지 않고 증거에서 유도한다

| 알고 싶은 것 | 어떻게 구하나 |
| --- | --- |
| 구현됐나 | `git log --all --grep=<ID>` — 커밋이 실제로 존재하는가 |
| 검증됐나 | `.codex/review/<ID>-*.verdict.md` 존재 + 그 파일의 판정 |
| 어느 단위까지 왔나 | `.codex/perf/units/<ID>-*.status` |

우리 원칙 **"완료 보고는 증거가 아니다 — 판정 기준은 항상 산출물 자체"** 와 같은 선이다.
상태 필드를 스펙에 적어두는 순간, 그 값은 산출물이 아니라 자기신고가 된다.

## 5. 스펙에 적지 않는 것 — 판정 · 상태 · 커밋 목록

- **판정**: 병렬 검증에서 단일 파일이 서로 덮어써서 **단위별 파일로 분리한 것**이고,
  `.codex/review/` 는 의도적으로 gitignore(로컬 전용)다. 커밋되는 스펙에 옮기면 그 분리가 무의미해진다.
- **상태**: 손으로 갱신하는 자기신고라 **조용히 낡는다** — §4 가 대신한다.
- **커밋 목록**: `git log --grep=<ID>` 가 항상 최신이다. 손으로 적은 목록은 갱신을 한 번 놓치는 순간 거짓이 된다.

## 6. 위임장 보관 — 스펙 파일 안에 남긴다

사용자 지시가 원본이다: "위임장은 docs 에 남겨서 계속 관리해야함."
(`docs/specs/2026-08-31-review-gates-redesign.md` ③)

- **M급 이상(ID가 발급된 작업)의 위임장 본문은 그 작업의 스펙 파일 안에 남긴다** — 하위 ID별로
  `## 위임장 <ID>-A` 절 하나씩. 별도 디렉터리나 새 파일 종류를 만들지 않는다 — 이 규약의 첫 줄
  그대로, Work Order는 새 계층이 아니라 기존 스펙에 얹는 것이다.
- **보관 시점은 분배 직전이고, 남기는 것은 확정본 그대로다.** 일꾼에게 실제로 나간 프롬프트와
  스펙 안의 절이 같은 텍스트여야 나중에 "무엇을 시켰나"를 되찾을 수 있다 — 요약본·가공본을 남기면
  §4의 우선순위 규칙(사용자 원문 > 스펙 > 위임장의 요약)을 대조할 원본이 사라진다.
- **§5와 어긋나지 않는다**: 스펙에 적지 않는 것은 판정·상태·커밋 목록 — 갱신을 놓치면 거짓이 되는
  값들이다. 위임장은 상태가 아니라 **지시**라서 저장해도 낡지 않는다. 한번 나간 위임장은 사실로
  고정되고, 재위임으로 새 위임장이 나가면 절을 하나 더 붙일 뿐 이전 절을 고치지 않는다.
- **S급 경량 위임은 남기지 않는다** — §2와 같은 선이다. 오타 수정에 보관 절을 만드는 것이
  "프로세스가 제품보다 복잡해지는" 실패다.
- 누가 언제 적는가(분배 절차 안의 자리)는 행동 규칙이라 `.codex/roles/orchestrator.md`가
  단일 원본이다 — 여기는 보관 위치·형식·시점만 정한다.

## 7. 이 규약이 다루지 않는 것

- **릴리즈 노트 연결** — 버전 규칙·노트 형식·RN 번호의 단일 원본은 `docs/releases/README.md` 다. 여기서 새로 배선하지 않는다.
- **Notion 반영** — 무엇이 동기화되는지의 단일 원본은 `.codex/rules/notion.md` 다. 여기서 새로 배선하지 않는다.
