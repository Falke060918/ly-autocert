# Shell traps — the tooling between you and the command

> Always loaded: `CLAUDE.md` imports this file with `@`, so it is in context from the first turn of every session — there is no `paths:` gate, because the trap springs on a one-off command line rather than on a file you opened. Where `@` imports are unsupported, read it directly before writing or debugging a shell script, a hook, or a command line.

These are properties of the outside tooling — the OS, awk, curl, git, MSYS, the rtk wrapper — not of this repository, so no amount of template fixing removes them: code newly written in a derived project walks into them again. What they share is silence. Each one either exits 0 or names the wrong culprit, so the cost is never the failure itself but the time spent looking in the wrong place.

## Encoding and locale

- **On Windows, `python -c "print(...)" > file` corrupts Korean text.** stdout is `cp949`, so the redirect damages the UTF-8 while the source file stays intact — which sends the diagnosis to the wrong file. Write bytes instead of printing: `open(path,'wb').write(s.encode('utf-8'))`.
- **macOS's default awk answers `==` between two all-Hangul strings as true, always.** In a UTF-8 locale `1*("표식"=="표현")` prints 1 from a BEGIN block (under `LC_ALL=C` it prints 0), so one equality guard silently discarded 18 of the table rows it was filtering and the script still exited 0. `index()` is not affected — compare with `index($0, "…")` (as `scripts/ko-wordcheck.sh` does), or pin `LC_ALL=C` when the comparison has to be byte-exact.
- **A `~` used as the `s///` delimiter collides with Korean range notation, and the whole `sed -f` script then applies nothing.** Korean prose writes a range as `5~15배` where English writes `5-15x`, so a substitution spelled `s~old~new~` has the tilde inside its own body read as a delimiter: on macOS sed exits 1 with `bad flag in substitute command`. The cost is not that one line. sed compiles the entire script before applying any of it, so **every** substitution in the file is dropped and the target comes back byte-identical — which reads as "none of my patterns matched" and sends the diagnosis to the patterns. Pick a delimiter the body cannot contain (`%`, `|`) when substituting in Korean text, and confirm the file actually changed instead of trusting the absence of a diff.

## Every layer eats one backslash — silently, at rc=0

Three layers do this, and none of them warns:

- The **Bash tool** performs one round of `\\` unescaping before bash ever sees the string.
- The **rtk hook wrapper** strips one backslash layer from a **space-free** pattern argument, so `grep -c '^\*\*'` actually runs as `^**` — still a valid BRE, so it matches every line and exits 0 (measured on rtk 0.44.0; a pattern *containing a space* passed through intact).
- **`awk -v var=value` interprets escapes inside the value**, so a Windows path handed to it loses `\S` → `S` and turns `\t` into a real TAB that then breaks any JSON consumer downstream.

Same family: **the Bash tool refuses a command string that carries a literal U+FFFD**, rejecting the whole call as "control characters" — so an inline fixture with that character pasted into it never runs at all.

Fix: never route an escape-sensitive value through a layer. Hand it to awk through the environment, which does no interpretation (`VAR=... awk '...ENVIRON["VAR"]...'`), generate fixtures into files and pipe them, and build odd characters with `chr(...)`. When a count is a gate, count with `awk '{n+=gsub(/re/,"")} END{print n+0}'` — rtk does not rewrite `awk`, and unlike `grep -c` it counts occurrences rather than matching lines. But `gsub` takes a **regex**, so a literal string carrying regex metacharacters silently counts the wrong thing: `gsub("결정 완료 (8)","")` reads the parentheses as a group and answers 0 for a heading that is right there, reporting a present section as missing. Count literals with `grep -oF … | wc -l` and keep `gsub` for patterns you actually wrote as patterns.

The rtk hook itself stays on — a standing decision (2026-09-01): accuracy outranks token savings, but avoidance is enough, so the wrapper is kept for its compression rather than removed for this one flaw. The behavioural rule that makes the two coexist: when a pattern search gates a decision — a grep-family command carrying a space-free regex argument whose match count or rc you are about to branch on — do not let it ride the rtk rewrite path. Reach for the routes above by default (`awk '{n+=gsub(/re/,"")} END{print n+0}'` for patterns, `grep -oF … | wc -l` for literals), and when the original command really is needed as written, run it unrewritten with `rtk proxy <cmd>`.

## The rc you read is not the command you care about

- **Empty stdout is not success.** In a non-git directory `git status --porcelain` exits 128 with empty output, so branching on "empty means a clean tree" reads the failure as success — and an unrecoverable delete goes through without a word.
- **A pipeline's rc belongs to its last stage.** In `git commit ... | tail`, a commit that actually failed still reports rc=0.
- **macOS's BSD `date` has no `-d`, so a GNU-only date guard is a permanent no-op there.** `date -d 2026-01-01 +%s` exits 1 with `date: illegal option -- d`, and the usual `$(… 2>/dev/null)` capture turns that into an empty string, which a "stay silent when unsure" branch reads as *not stale*. `scripts/session-markers.sh`'s `MAP-STALE` check therefore never fires on macOS (measured 2026-08-29) and says nothing about it, so "the marker doesn't show up" gets diagnosed as a bug in the marker. To exercise such a path, put a GNU-style `date -d` shim first on `PATH`: the same repository then printed `TEMPLATE-REPO MAP-STALE` instead of `TEMPLATE-REPO`.
- **curl exits 0 on a 404.** Without `-f` the 404 body gets written, leaving a 0-byte file and a successful exit; upstream layouts move, so `raw.githubusercontent.com` paths go stale on their own.
- **A nested headless session's `stream-json` mixes a subagent's `tool_use` into the same stream as the main session's.** When you judge "what tool did the main session call directly" from `claude -p --output-format stream-json --verbose`, counting `"name"` fields alone reads a *delegated* `Write` as one the main session ran itself — so delegation enforcement that is working reads as broken, silently and at rc=0. Only events whose `parent_tool_use_id` is `None` are the main session's own calls; anything with a value happened inside a delegation. Two runs of the same prompt on CLI 2.1.203 showed it: with no flag the main session ran `Bash` directly, while under `--agent orchestrator` the main session called only `Agent` and the `Write` happened inside the delegation — both runs produced the same output file. Note also that this CLI names the delegation tool `Agent`, not `Task`, so grepping for `Task` counts zero delegations.
- **A headless session (`claude -p`) has no `AskUserQuestion` tool at all, and the plain-text question you fall back to is a dead end.** Handed an ambiguous instruction and asked to clarify it, the session answered: "I don't have an `AskUserQuestion` tool in this session — my available tools are Agent, Bash, Edit, Glob, Grep, PowerShell, Read, ReportFindings, ScheduleWakeup, Skill, ToolSearch, Workflow, and Write..." (CLI 2.1.203 on Windows, measured once, 2026-08-31). A question written as prose instead leaves as the session's final output, so there is no turn in which anyone can answer it, and the run still exits 0 — a decision nobody ever made reads as a finished job. The paired run did not even ask: it closed the same ambiguous instruction with "investigate and report" and called `AskUserQuestion` zero times. What to do instead is a behaviour rule rather than a fact — it lives in `.claude/agents/orchestrator.md` 'User communication'.
- **A git shim on `PATH` can fail silently, and the test it was built for then reads a stale artifact as a pass.** Hit while verifying a compression hook: a shim that ended with `exec /usr/bin/git "$@"` fails on Git Bash, so the script under test never ran git at all — but the previous run's output was still on disk, got read as this run's result, and the check reported "pass". Exec the real path instead (`/mingw64/bin/git`), and before trusting a shim-mediated run, confirm the shim actually applied by the artifact's timestamp.

Fix: judge by `rc=$?` of the command itself — never by emptiness, and never through a pipe (drop the `| tail`, or set `pipefail`, whenever the rc is what you are testing). The rtk wrapper preserves exit codes, so this holds through the hook too. After a download, check the file size right away, and resolve doubtful paths through the git trees API.

## A hook named for finishing also fires while the subagent is still alive

- **`SubagentStop` does not fire only at a subagent's end: it also repeats throughout that subagent's lifetime, and those repeat lines carry an empty `agent_type`.** Measured 2026-09-01: with one subagent alive the repeat came about every 32.5s, with three alive about every 11s — the interval appears to shrink as live subagents multiply. The official hook documentation says only "When a subagent finishes", so anything written against that wording counts every repeat as one more delegation. Nothing errors and every line is well-formed JSON, so the number simply looks busy: one session's log held 311 rows of which 272 were not delegations, and across 14 logs the counts fell 311→39, 346→69, 210→25 and 57→8 once filtered.
- **Why the event repeats while the subagent is alive is unknown.** It was not diagnosed, only observed — do not build on a guessed cause.

Fix: treat a populated `agent_type` as the test for a real termination. Start counts and type-bearing stop counts matched exactly in every session checked (39/39, 22/22, 25/25). The payload also carries `agent_id` — a 16-hex-digit value that is stable per subagent instance (one reviewer instance's single start and all 41 of its tool hooks shared one value), documented as "Unique identifier for the subagent. Present only when the hook fires inside a subagent call". Key on it: without it there is no way to attribute a stop to the right instance when two subagents of the same type overlap.

## A rules file without `paths:` is loaded into every session

- **A `.claude/rules/*.md` carrying no `paths:` frontmatter goes into the initial context whole — even when `CLAUDE.md` never `@`-imports it.** Seen both ways in one session (2026-09-01): `korean-style.md` and `korean-wordlist.md`, neither an `@` target and neither carrying `paths:`, were already in the first turn's context, while `memory.md`, which does carry `paths:`, was absent until `docs/MAP.md` was read. The CLAUDE.md conditional-load table says only that a rule loads "when you touch the related files", so a file *missing* from that table reads as not loaded rather than as always loaded, and nothing warns either way. The cost is not rounding error: putting `korean-wordlist.md` behind `paths:` alone dropped the always-injected bytes from 96,040 to 90,883 (`cdba949`).

Fix: when the context feels heavy, do not start from the CLAUDE.md body or the size of STATE — sweep `head -5 .claude/rules/*.md` for the frontmatter first. And decide `paths:` deliberately for every new rules file: when always-on is not the intent, add the frontmatter and a row to the CLAUDE.md conditional-load table. Skipping that decision does not leave the file unloaded; it silently makes it permanent.

## MSYS path conversion (Git Bash on Windows)

- **`gh api /markdown` dies on it**: the leading slash gets rewritten into `invalid API endpoint: "C:/Program Files/Git/markdown"`. Drop the leading slash, use the raw endpoint, and declare the body plain text — `MSYS_NO_PATHCONV=1 gh api --method POST markdown/raw -H "Content-Type: text/plain" --input <file>`. Plain `markdown` wants a JSON body (400), and `markdown/raw` without that header is refused as the wrong media type (415). GitHub's own renderer then verifies Markdown tables for real.
- The same conversion rewrites **inline colon-bearing revspecs**, so `git show template/main:scripts/…` is unsafe on that platform. Check for a path with `git ls-tree --name-only <rev> -- <path>` (a pathspec is not converted), and pass revspecs as list arguments through `subprocess.run` rather than building a command string.

## The sandbox denies a bash write where the Edit tool goes through

- **Writing into `.claude/skills/**` from bash fails with `Operation not permitted` — `python -c 'open(path,"w")…'`, a heredoc redirect, `cp`, all of them — while the Edit tool writes the very same path without complaint.** The message names the path, so it reads as a directory permission to be widened in the sandbox allowlist; the variable is the *tool*, not the path. Two agents walked into it in one session (2026-08-29) and each spent its own time on the wrong culprit.

- **A read-only-looking command can still be a write.** `python3 -m py_compile <file>` — reached for as a syntax check after `python3 -c` is refused by the deny list — writes its bytecode under `~/Library/Caches/com.apple.python` and dies there, so a passing file reports as a failing one. Point the cache at a writable place instead: `PYTHONPYCACHEPREFIX="$TMPDIR/pycache" python3 -m py_compile <file>`.

- **A heredoc is not a way past the `python -c` deny rule.** `python3 - <<'PY' … PY` reads as a different command — no `-c` flag in sight — but it is refused just the same, so the detour buys nothing and costs the turn spent building it (2026-09-05, a `/handoff` worker doing a text substitution). Do not go looking for a shell spelling that slips past: substitute text with the Edit tool.

- **`git merge` is a bash write too, and when it dies there it dies halfway.** Reaching a file under `.claude/skills/**` the merge aborts with `Operation not permitted`, leaving `HEAD` exactly where it was while the working tree has already been updated in part — neither merged nor rolled back. The message names only the path, so nothing says the tree is now half-updated; `git status` afterwards looks like a pile of uncommitted edits somebody made by hand. Recovery is lossless as long as those leftovers are byte-identical to the incoming side: confirm that first (`git diff <merged-ref> -- <paths>` comes back empty), then `git checkout -- .` to throw them away and re-run the merge with the sandbox disabled.

- **The sandbox also blocks the loopback and local sockets, and a CLI that talks to a local app through them fails silently at rc=0.** Measured in a derived project (2026-09-05): inside the sandbox `curl` to `127.0.0.1` came back `000`, a local socket connect was refused, and `orca status --json` exited 0 with `ok: true` and well-formed JSON whose payload said `connectionState: "disconnected"`, `reachable: false`, `running: false, pid: null` — while `orca worktree list --json` answered `runtime_unavailable` with "Could not connect to the running Orca app. Restart Orca and try again." Outside the sandbox the same app (pid 54902) was connected and listing worktrees. Nothing names the sandbox: the only trace is a `SecCodeCheckValidity` line on stderr, and the JSON reads exactly like an app that is off — so the session skipped Orca dispatch on an app that was up. The same shape awaits any local-daemon CLI (docker, a language server, a desktop app's control socket).

- **Hooks run outside that sandbox, so the identical request succeeds from a hook and fails from the Bash tool.** This is the other side of the wall above, and the documentation describes only one side: `https://code.claude.com/docs/en/sandboxing` says the sandbox "applies only to Bash commands and their child processes" and never states the converse, so nothing tells you a hook is exempt — the natural reading is that a sandboxed session is sandboxed throughout. Two agents reproduced it separately in one session (2026-09-05), same session and same port: a loopback request issued from a hook reached the server and came back 404 at rc=0, while the same request from the Bash tool died at rc=7 (one of them injected a SessionStart hook through a throwaway `--settings` to get there). The consequence is practical — a check that has to see the outside world (a local app's control socket, a daemon's port) can be **placed in a hook** and answered honestly there, which is what `scripts/session-banner.sh` does for its `ORCA-APP-*` suffix; one `orca status --json` took 0.15–0.19s, cheap enough for session start. It cuts the other way too: a hook has none of the sandbox's protection, so whatever it runs has the user's full reach.

Fix: change files with Edit/Write and keep bash for reading, searching, and git — except a git command that writes the working tree (`merge`, `checkout`, `stash pop`), which walks into the same wall and needs the sandbox disabled. When a bash write does come back `Operation not permitted`, re-run the same change through Edit before proposing any allowlist edit — and when the command was not meant to write at all, look for where it caches before widening anything. And when a local-app CLI reports "disconnected" from inside the sandbox, treat it as *unreachable from here*, not as *off*: re-run it with the sandbox disabled and confirm the process itself before concluding anything — for Orca the rule that does this is `.claude/rules/orca.md` §0.

## Windows PowerShell 5.1

These are properties of the shell itself, not of a wrapper around it. What they share with the rest of this file: only the first one is honest about its cause — the other two surface as a garbled diff or a null-reference error on an unrelated line, so the encoding is the last thing you suspect.

- **Windows PowerShell 5.1 cannot use `&&` as a statement separator.** A one-liner joined with bash syntax dies with `'&&' 토큰은 이 버전에서 올바른 문 구분 기호가 아닙니다`. The separator is `;`. This is version-bound: PowerShell 7+ does support `&&`, so a command that works when you test it may fail on a 5.1 host — assume `;` when you don't know the version.
- **`Set-Content -Encoding utf8` writes a BOM on PowerShell 5.1.** Used to splice one line into a JSON file, it prepended U+FEFF, and the diff showed only `-{` / `+{` with no visible cause. Node's `JSON.parse` throws on a leading BOM, so `.claude/settings.json` could fail to load whole — taking the hooks and the permission config down with it. To write without a BOM use `[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($false)))`. Verify by the bytes, not the eye: `head -c 3 <file> | od -An -tx1` prints `7b 0a 20` when there is no BOM, `ef bb bf` when there is.
- **PowerShell 5.1 reads a BOM-less `.ps1` as ANSI (cp949 in a Korean locale), not UTF-8.** So a script an agent wrote with the Write tool, carrying Korean comments, has those lines corrupted — and the error fires not at the corrupted line but somewhere far downstream: in one run a much later `$t.Contains(...)` died with `null 값 식에서 메서드를 호출할 수 없습니다`, which points the diagnosis at logic rather than at encoding. Fix: keep any `.ps1` an agent generates to ASCII only (English messages too), and print a `FAIL:` line at each step so the script says where it died on its own.
